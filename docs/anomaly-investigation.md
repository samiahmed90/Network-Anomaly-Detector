# Network Anomaly Investigation

## 1. Overview

This investigation examines an unusual network traffic record identified by the Isolation Forest anomaly detection model in the Network Anomaly Detector project.

The objective was to understand the traffic characteristics that caused the model to flag the record and determine whether packet-capture behavior could have influenced the extracted features.

**Investigation details:**

- Monitored device: `192.168.50.10` (Windows test VM)
- Flagged timestamp: October 6, 2026, 19:35
- Detection algorithm: Isolation Forest
- Data source: SQLite packet database (`network.db`)
- Sensor interface: `enp0s8` (Ubuntu sensor VM)

## 2. Machine Learning Detection Results

The initial Isolation Forest model was trained using 80% of the chronological dataset and evaluated using the remaining 20%.

| Metric | Result |
|---|---:|
| Total records | 170 |
| Training records | 136 |
| Testing records | 34 |
| Normal predictions | 33 |
| Anomaly predictions | 1 |

The model identified one potential anomaly among the 34 test records.

**Important:** This result does not represent 97.1% detection accuracy. The dataset does not contain verified labels indicating which records are normal or malicious. The model identifies unusual patterns rather than confirming attacks.

### 2.1 Flagged Record

The flagged record contained the following features:

| Feature | Observed value |
|---|---:|
| Packet count | 187 |
| Total bytes | 164,930 |
| Average packet size | 881.98 |
| TCP packets | 179 |
| UDP packets | 8 |
| Unique destinations | 12 |
| Unique destination ports | 1 |
| DNS packets | 0 |

The average packet size was approximately 2.06 standard deviations above the training mean.

The packet count, total bytes, and other individual features were not unusually high compared with the training data. This suggests that the model identified an unusual combination of traffic characteristics rather than a single extreme feature.

## 3. Packet-Level Investigation

The SQLite database was queried to examine the traffic generated by the Windows VM during the flagged minute.

### 3.1 Traffic Direction

The database contained:

- 187 outgoing packets from `192.168.50.10`.
- 761 incoming packets to `192.168.50.10`.
- 948 total packets involving the device during that minute.

The feature extraction process counted outgoing packets for the device-level record. This explains why the feature table reported 187 packets rather than 948.

### 3.2 Protocol and Port Distribution

All 187 outgoing packets used destination port `443`.

| Protocol | Destination port | Packets | Total bytes |
|---|---:|---:|---:|
| TCP | 443 | 179 | 154,594 |
| UDP | 443 | 8 | 10,336 |
| **Total** | | **187** | **164,930** |

TCP port 443 is commonly used for HTTPS traffic. UDP port 443 can be used by QUIC and HTTP/3.

These port numbers alone do not establish whether the traffic was legitimate or malicious.

### 3.3 Destination Analysis

The Windows VM communicated with 12 unique destination IP addresses.

The busiest destinations included:

| Destination IP | Protocol | Packets | Total bytes |
|---|---|---:|---:|
| `74.125.172.74` | TCP/UDP | 102 | 71,069 |
| `142.251.154.4` | TCP | 21 | 19,058 |
| `142.250.217.238` | TCP/UDP | 14 | 57,616 |
| `142.251.163.100` | TCP | 11 | 6,052 |
| `142.251.179.84` | TCP | 9 | 7,209 |
| `8.8.8.8` | TCP/UDP | 14 | 6,307 |
| `8.8.4.4` | TCP | 7 | 889 |

Several of these addresses are associated with Google infrastructure, including the well-known Google Public DNS addresses `8.8.8.8` and `8.8.4.4`.

However, destination ownership and application-level behavior were not fully verified during this investigation.

### 3.4 Large TCP Records

Further investigation focused on destination `142.250.217.238`, which accounted for 53,740 bytes.

Three TCP records accounted for 50,148 bytes:

| Timestamp | Packet size |
|---|---:|
| 19:35:35 | 20,494 bytes |
| 19:35:35 | 16,460 bytes |
| 19:35:35 | 13,194 bytes |

These three records represented approximately 93% of the bytes sent to that destination.

The large recorded packet sizes contributed substantially to the unusually high average packet size observed by the machine learning model.

## 4. Packet Capture and Offloading Investigation

The investigation identified that the Ubuntu sensor's network interface, `enp0s8`, had the following offloading features enabled:

- TCP Segmentation Offload (TSO)
- Generic Segmentation Offload (GSO)
- Generic Receive Offload (GRO)

These features allow the operating system and network stack to process larger packet buffers or segments before or after segmentation.

In virtualized environments, packet captures can therefore report packet sizes that do not correspond directly to individual packets transmitted over the physical network.

This could have influenced the packet-size measurements used by the anomaly detection model.

### 4.1 Configuration Change

The following command was used to temporarily disable the three offloading features:

```bash
sudo ethtool -K enp0s8 tso off gso off gro off
```

The settings were subsequently verified as disabled.

**Note:** A fresh capture and comparison after this configuration change has not yet been documented. Therefore, the effect of offloading on the flagged record remains a hypothesis rather than a confirmed cause.

## 5. Investigation Findings

The investigation established the following:

1. The Isolation Forest model successfully identified an unusual traffic record.
2. The flagged minute contained 187 outgoing packets, all using destination port 443.
3. Three large TCP records contributed approximately 50 KB of traffic to one destination.
4. The average packet size was substantially higher than the training mean.
5. TSO, GSO, and GRO were enabled on the Ubuntu sensor interface before the investigation.
6. These settings were disabled to reduce potential packet-capture measurement artifacts.

No confirmed malicious activity was identified.

The event should therefore be classified as a **potential network anomaly requiring further validation**, not a confirmed security incident.

## 6. Limitations

The investigation has several limitations:

- The model was trained on a relatively small dataset of 170 one-minute records.
- The dataset represents one Windows test VM rather than a diverse network of devices.
- No labeled malicious traffic was available to validate detection performance.
- Encrypted traffic limited application-level inspection.
- Packet offloading may have influenced captured packet sizes.
- Destination IP ownership and the purpose of each connection were not fully verified.

These limitations should be considered when interpreting the model's predictions.

## 7. Future Improvements

The following improvements are planned:

1. Collect additional baseline network traffic with the updated capture configuration.
2. Compare packet-size distributions before and after disabling offloading.
3. Expand monitoring to support multiple devices.
4. Improve feature extraction and evaluate additional behavioral features.
5. Test the detector using controlled abnormal traffic scenarios.
6. Develop a Flask dashboard to display network statistics, monitored devices, and anomaly alerts.
7. Integrate automated detection and alert generation into the monitoring application.

## 8. Conclusion

This investigation provided insight into how the initial anomaly detection model identifies unusual network behavior.

The flagged event was associated with a relatively high average packet size and several unusually large TCP records. The discovery of enabled packet-offloading features introduced an important potential measurement limitation that needs to be tested.

Although no malicious activity was confirmed, the investigation helped identify areas where the data collection and feature extraction pipeline can be improved.

The findings will guide further development of the Network Anomaly Detector, particularly the integration of reliable anomaly detection with a Flask-based network monitoring dashboard.
